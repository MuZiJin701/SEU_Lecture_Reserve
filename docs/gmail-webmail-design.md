# Gmail 网页发信需求澄清

2026-10-19，状态：实验结束，本机网页登录被拒绝。用户选择继续完善 SMTP，最终范围见[邮件通知需求](notification-requirements.md#smtp-多邮箱方案确认2026-10-19)。以下保留探索过程；模板已移除实验字段，不再要求配置网页登录密码。

## 已确认的需求

- 寻求新方案的主要原因是本机 SMTP 连接失败，而非单纯追求技术统一或免应用专用密码。已有网络采样见[使用指南](usage.md#开发与验收)，历史结果不代表当前网络状态。
- 首期仅支持 Gmail 网页作为发件服务；不承诺所有邮箱网页通用。
- 要求通过配置好的 `.env` 自动登录并发送，不接受以首次人工登录为前提的方案。
- 使用 Playwright 管理的 Chromium；邮箱启动独立于学校浏览器的实例，不依赖学校浏览器的登录和生命周期。
- 实验期间曾在模板提供 `GMAIL_USERNAME` 和 `GMAIL_PASSWORD` 空值，由用户复制到本机 `.env` 后填写。正式脚本一直不读取这两项，`--test-mail` 仍使用 SMTP；实验结束后移除模板字段。

## 已核实的限制

- 当前 SMTP 实现只有 `SMTP_SSL`，没有 STARTTLS 或网页发信。既有文档记录的一次本机测试在连接阶段失败，尚未进入认证，不能据此判断应用专用密码错误。
- 当前学校 Chromium 使用临时会话，没有可直接复用的持久化邮箱登录态。
- Google 明确说明可能阻止通过软件自动控制的浏览器登录；使用 Chromium 不保证自动登录成功。见[受支持浏览器说明](https://support.google.com/accounts/answer/7675428?hl=zh-Hans&co=GENIE.Platform%3DDesktop)。
- 开启两步验证的账号使用密码登录时还可能需要额外验证；仅有 `.env` 中的账号和密码不能保证完成这些步骤。见[两步验证说明](https://support.google.com/accounts/answer/185839?hl=zh-Hans)。
- Gmail 网页登录需要 Google 登录凭据，当前 SMTP 应用专用密码不能直接当作网页登录密码。

## 尚待决定

- 自动登录遇到额外身份验证或被 Google 拒绝时，是否接受仅记录通知失败并继续预约，不等待人工处理，也不保证该通知送达。

## 本机验证结果

2026-10-19，按用户授权在本机 `.env` 中将 `SMTP_USERNAME` 的值复制到 `GMAIL_USERNAME`、`SEU_PASSWORD` 的值复制到 `GMAIL_PASSWORD`，未将真实值写入模板或输出到日志。

使用项目 Playwright 管理的 Chromium，独立有头实例、临时会话，访问 Gmail 登录入口。首次探测未匹配当前页面的账号输入框；改用页面实际的账号字段后成功提交账号，Google 随即提示浏览器或应用可能不安全并拒绝继续。没有提交密码、发送邮件或保存登录态，也没有尝试规避自动化检测。

结论：本机本次采样未通过 `.env` 自动网页登录方案；不能据此判断密码错误，也不能推断所有账号或所有环境均会失败。若要继续寻找替代方案，需要重新讨论认证方式，例如 Gmail API 的一次性 OAuth 授权是否可接受。

### 进一步诊断

同日使用本地诊断脚本复现：提交账号后，Google 将页面转到 `accounts.google.com/v3/signin/rejected`，显示“此浏览器或应用可能不安全”。这次复现的登录页 HTTP 状态为 200，相关账号请求返回 200／302／204，没有记录到浏览器网络请求失败。阻断发生在进入密码页之前，不能将此结果解释为密码错误、两步验证失败或发信失败。

保持账号、Chromium 构建及有头模式不变，不改动网络配置，逐项对照；没有另行查询公网 IP，不能保证代理实际出口始终相同：

| 启动方式 | 结果 |
| --- | --- |
| 项目原有 `setup_browser`，临时上下文 | 转到拒绝登录页面 |
| 去掉项目额外的 GPU 和窗口尺寸参数 | 转到拒绝登录页面 |
| 其余保留原设置，仅启用 Chromium 沙箱 | 转到拒绝登录页面 |
| 其余保留原设置，改用新建的持久化上下文 | 转到拒绝登录页面 |

四组均使用 Chromium `156.0.8078.4`，页面均可读取 `navigator.webdriver=true`。沙箱组实际命令行不含 `--no-sandbox`，确认设置已生效。持久化组使用空白临时用户数据目录，并未复用曾成功登录的可信会话；不能用这组结果否定已有可信会话的作用。

这些对照表明，单独调整 GPU／窗口参数、沙箱或上下文类型没有解决本次拒绝。自动化状态是可见线索，结合 Google 官方列出的[自动控制浏览器可能被阻止](https://support.google.com/accounts/answer/7675428?hl=zh-Hans&co=GENIE.Platform%3DDesktop)，与登录环境检查相符；尚无因果对照证明 Google 仅依据 `navigator.webdriver` 判定，也未排除 Chromium 构建、账号或网络出口因素的组合影响。Google 页面未给出内部判定项，不能把推测写成已确认根因。

诊断未更换系统浏览器、账号、网络出口或代理配置，未隐藏自动化特征、提交密码或发送邮件。诊断脚本与脱敏输出保存在已被 Git 忽略的 `state/gmail-diagnostics/`。本地可用 `uv run --locked python state/gmail-diagnostics/probe.py baseline` 复现：它会真实提交配置的账号，并以是否进入密码页判定；拒绝时返回非零退出码。当前复现仍失败，没有修改正式预约或通知实现。

下一项有区分度的对照是同一份 Chromium 在不被 Playwright 控制时，由用户只提交账号、观察能否进入密码页。此项需要人工输入，已向用户询问是否参与，尚未执行；也未把人工登录作为最终通知方案。

用户随后要求验证 Gmail API 方案。本机匿名网络检查已通过，授权与投递尚待验证，具体结果和后续步骤见 [Gmail API 本机可行性验证](gmail-api-validation.md)；尚未决定替换正式通知实现。
