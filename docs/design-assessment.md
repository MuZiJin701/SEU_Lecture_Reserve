## 当前原理

Python 通过 Playwright 同步 API 控制本机 Chrome，读取讲座卡片并模拟输入、点击；学校服务端决定是否取得名额。主流程未调用讲座查询或预约 HTTP 接口。

```text
执行入口 → 读取并校验配置 → 初始化本地 OCR / Chrome
  → 填写账号密码 → 等待跳转与人工短信认证
  → 刷新预约页 → 解析、筛选并排序讲座 → 选择第一候选
  → 点击“预约” → 识别并填写图形验证码 → 提交
  → 核对目标按钮变为“取消预约”：退出并关闭浏览器
  → 未确认成功：至多三次尝试，再继续扫描
```

- `browser.py` 共享 Chrome 启动、登录及秒到毫秒的超时转换。Windows 从 App Paths 发现非默认安装位置，其他平台使用 Chrome 通道；无需 ChromeDriver。
- `main.py` 负责讲座解析、筛选、排序和预约；`captcha_ocr.py` 复用登录流程采集验证码样本。
- 导入两个入口均不读取配置、不初始化 OCR、不启动浏览器，执行脚本才开始运行。
- OCR 仅识别图形验证码，不代替短信认证，也不保证获得预约名额。
- 配置的 0.05 秒是扫描后的额外休眠；未测量完整周期，不能据此宣称每秒扫描 20 次。

## 已确认的迁移范围

用户明确选择 Playwright，并确认以下边界：

1. 迁移预约主程序及验证码采集入口，同时处理成功确认、等待与浏览器清理。
2. 保留现有筛选与排序语义，包括指定标题跳过其他筛选。
3. 保留可见 Chrome、人工短信认证及预约一场成功后退出。

两个入口共用启动与登录代码，保留 Chrome 自动发现和 `--enable-logging` 排除。元素操作使用 Locator 自动等待；登录提交后等待返回预约页，不再固定休眠完整的跳转等待时间。Playwright 等待超时为 0 会表示无限等待，配置转换因此至少使用 1 毫秒。

导航、元素操作和预约确认共用 `SEU_TIMEOUT_ELEMENT_WAIT`（默认 3 秒）；登录提交后的跳转等待使用 `SEU_TIMEOUT_LOGIN_REDIRECT`。登录加载和异常恢复刷新后仍可额外休眠 `SEU_TIMEOUT_PAGE_LOAD`；提交预约后先等待 `SEU_TIMEOUT_ACTION_CONFIRM`，随后等待目标卡片状态。

成功判断不再使用整页“成功”文字或离开预约页的 URL。提交前后重新定位目标讲座，只点击精确文字“预约”的按钮，目标按钮变为“取消预约”才确认成功；无法唯一定位的同名讲座暂缓提交。该策略依赖页面更新目标卡片，真实系统如只显示提示而不更新卡片，需调整确认方式。

浏览器在正常结束、异常和中断时通过 finally 清理；强制结束进程仍可能残留浏览器。Playwright 错误日志可能包含填写内容，登录失败只输出异常类型，错误页面与截图仅留本地。

## 方案取舍

| 方案 | 价值与限制 | 当前状态 |
| --- | --- | --- |
| 保留 Selenium | 改动较少，但需继续维护驱动与等待逻辑；业务缺陷仍须单独修复 | 迁移前曾考虑 |
| Playwright 同步 API | 内建动作等待、Locator 重定位；仍依赖页面结构，也不证明预约更快 | 用户选定并已实施 |
| 浏览器认证 + 授权接口查询 | 若存在允许调用的稳定接口，可减少整页刷新；须核实接口、会话及令牌要求 | 未调查实际接口，留作后续候选 |
| 纯 HTTP 替换 | 可能减少浏览器依赖，但认证及业务接口证据不足 | 当前不实施 |

官方参考：[Playwright 自动等待](https://playwright.dev/python/docs/actionability)、[Chrome 通道](https://playwright.dev/python/docs/browsers#google-chrome--microsoft-edge)、[共享 Cookie 的请求上下文](https://playwright.dev/python/docs/api/class-apirequestcontext)。自动等待保证动作具备可操作条件，业务预约成功仍须独立确认；共享 Cookie 也不代表学校接口必然可用。

## 保留的限制与后续改进

| 限制 | 影响与改进方向 |
| --- | --- |
| 扫描等待卡片超时返回空列表，刷新成功时不触发重新登录 | 认证失效可能持续显示无讲座；应区分空列表、会话失效和加载异常 |
| 冲突检查只读取当前页面，查找异常返回无冲突，解析失败的卡片被跳过 | 日程未知可能被放行；可单独表达“无法检查”，并确认完整已预约日程来源 |
| 指定标题直接通过后续筛选 | 会跳过类别、校区、线上线下开关与冲突检查；本轮明确保留 |
| 校区排序仍将字符串与列表比较 | 常规模式下线上统一排在线下前；校区配置列表顺序不构成优先级 |
| 每轮只尝试排序第一场 | 第一场持续失败时会阻塞后续候选；可独立增加候选轮换 |
| 每个候选重新遍历并解析整页做冲突检查 | 最坏接近 O(n²) 次卡片解析；可每轮读取一次快照，再用普通数据筛选 |
| 目标身份暂用唯一标题 | 同名讲座会暂缓预约；若页面提供稳定讲座 ID，应改用该 ID |

以上均未包含在本轮迁移中。后续应先处理状态识别和信息不全，再测量刷新、解析、OCR 与确认耗时，决定轮询频率或接口方案；不预建服务端、数据库、多账号并发或 OCR 训练流程。

### 已核实的请求流程

```text
讲座入口 → 校外访问网关 → CAS 公钥与账号认证
  → 网关回调 → 按返回要求报告浏览器模式环境 → authCheck
  → 校外访问状态确认 → 讲座系统 CAS 会话复用
  → 应用配置 / 讲座列表 / 我的活动 / 图形验证码 / 预约前检查
```

- 网关初始化使用 `/passport/v1/public/authConfig`；校内账号通过 `/passport/v1/public/casLogin?sfDomain=CAS-auth` 导航到学校 CAS。
- CAS 公开前端位于 `auth.seu.edu.cn/dist/umi.32c0b43a.js`。实际验证了 `getChiperKey`、`casLogin`、`verifyTgt`：公钥需按 URL-safe Base64 解码为 DER，密码采用前端相同的 RSA PKCS#1 v1.5 加密。首次提交使用 `fingerPrint=null`，没有伪造受信设备指纹。
- `casLogin` 的 `200` 分支通过 `loginRedirect?redirectUrl=` 直接拼接已编码的响应字段，不能再次 URL 编码；`verifyTgt` 的 `201` 分支则直接导航响应 URL，不能套用前一种处理。
- CAS 回调返回的网关页面还携带后续步骤，取得该页面不等于完成认证。本次依次完成要求的 `reportEnv` 和 `authCheck`，保留 Cookie、CSRF 及 SDK 的客户端平台参数；未伪造前端 `online` Cookie 作为登录凭据。
